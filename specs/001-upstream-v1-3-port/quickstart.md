# Reproducible acceptance procedure

Use an isolated checkout and Python 3.11+ with requirements.txt. All consumer paths below are temporary fixtures, never real game repositories.

1. Run `python tools/validate.py`, targeted tests and `python -m unittest discover -s tests -v` after payload review/rebuild.
2. Compare helper output, exit status and changed files with fixed upstream `abc0de79d6ceb0b5d7aa693945849b3937afbe6a` on equivalent temporary inputs. Account only for documented native host paths/config differences.
3. Install into a temporary project. From installed templates make a small brief and browser playable, retain original words/Keep/Avoid, run scripted and no-input checks and view screenshots. Report it as a framework sample, not a model-generated quality assessment.
4. Revise a requested feature, apply fixed tuning, light-retest and share delivery. Verify imported source bytes remain unchanged and delivery excludes work files.
5. Grow from the copied prototype; record seed/inputs and compare actual replay, build, rules and smoke. Add/accept a feature, select cuts, verify numbering/story sync and restore. Check missing-browser and nonrepeatable branches remain unassessed.
6. Install frozen base 2.1.0 into another temporary consumer, add instructions/config/custom checkpoint/workbench/other skills, preview and upgrade. Restore context and reinstall; preserve all user files. Edited managed conflicts must stop before writes.
7. Rebuild release hashes, validate again, verify ancestry/mapping and run exact-head candidate CI. Record commands/results separately as FORMAT, EXECUTED and NOT ASSESSED in the PR.

Browser and package dependencies are installed only in temporary test tooling/consumers. Real Codex skill-session inference, native hook delivery, real engine builds and human fun/playtesting require distinct evidence.
